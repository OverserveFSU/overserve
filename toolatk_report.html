OverServe: Audited-Benign Tool Denial-of-Efficiency

An MCP tool that passes static code review + a prompt that passes log audit → the agent self-DoSes on a benign task, with no single-tool signature. internal research draft

Victim: qwen3.5 (EnterpriseOps-Gym Teams). Judges: GLM-5.3-flash. Cap = 40 tool calls. All numbers below are measured, with the honest caveats stated.

1 · Threat model

The attacker can do two things: (1) rewrite the user prompt, and (2) submit one MCP tool (a piece of software) that a SaaS platform audits and installs. Goal: denial-of-efficiency — make the agent burn its LLM-call budget on a task that still completes successfully (fidelity = 1), so it is stealthy and hard to attribute.

The core enabler: attacker control of the observation

Every prior prompt-only attack failed because the agent always self-terminates on a solvable task (it detects stagnation / infeasibility / completion). A submitted tool breaks that: the tool's return values are attacker-controlled, so it can forge a receding horizon the agent cannot recognize as stagnation.

2 · Where the malice hides — and why every audit misses it

The attack works by separating the malice across three places, none of which any single audit inspects:

The malice actually lives in: the tool's return message ("follow this checklist, then call me again") + a hidden adversarial data source whose documented completion signal never fires.
Mechanism (strategy B — correct code, adversarial data). The handler is textbook-correct: it checks the documented termination signal (drift is False, pending == 0, next_cursor is None) and would stop if the backing service ever reported completion. Static review approves it. But the real (hidden) data source never reports completion, so at runtime the handler returns a remediation checklist naming real tools and ending "…then call me again" — an infinite multi-tool cycle. The benign prompt only ever says, once: "run X and follow any checklist it returns."

4 · Optimizing the search — the attack is a class, not a point

Problem

The greedy actor–critic search (v5) mode-collapsed — it found one good tool and produced five variants of it. That can't tell a lucky one-off from a systematic vulnerability.

Fix: Quality-Diversity (MAP-Elites)

Bin candidates by a behavioral niche = (loop's dominant real write-tool) × (# distinct loop tools), keep the best per niche, force the writer to fill empty niches (+ dedup). Both LLM judges denoised (median-of-3). Adaptive rollouts (n=3 screen → n=6–8 confirm).

The 12-niche map (best elite per niche)

amp = mean calls / 40 · cap = fraction hitting the hard cap · cyc = cycle-stealth (1 − dominant-tool share) · tool/prompt = audit pass scores. corner = amp≥.7 ∧ cyc≥.5 ∧ tool≥.8 ∧ prompt≥.7 ∧ fid=1.

Structure the map reveals (defender-useful)

  • update / mixedWrite routes reach the corner (clean prompt) but are cap-unstable (0.17–0.50).
  • send_channel_message routes reliably hit the full cap (1.0) but are prompt-leaky (0.40–0.60) — "record/log an entry" reads more directive than "run a check".
  • 2-tool cycles amplify weakly (agent disengages fast); 4-tool cycles both amplify more and lower attack-share.
  • edit route (update_channel_message) is inherently dead — the gym forbids message-body edits, so that loop cannot complete (amp ~0.20). Not every real tool can host the cycle.

6 · Honest verdict & caveats

Established: a tool that passes static code review and a prompt that passes log audit reliably cause a fidelity-preserving, four-axis-stealthy, multi-tool denial-of-efficiency — ~83–94% of budget burned on average, task completes — and this holds for a class of distinct mechanisms, not one lucky tool.
  • Not a reliable hard-cap exhaustion — cap-rate is 0.30–0.60 depending on mechanism. The DoS is wasted compute (matches "denial-of-efficiency"), not a hard crash.
  • Victim tested = qwen3.5 only. Cross-model generalization not yet measured.
  • Auditors are GLM LLM-judges, not humans. Denoised (median-of-3/15) but not human-validated.
  • Relies on an adversarial data source whose real behavior contradicts its documented contract — the paper must state this assumption (models "tool backend behaves unlike its docs").

7 · Defense

Static code review and prompt/log audit are both insufficient — the defect is in neither the code (it's in the data) nor the prompt (it's a benign goal). The only effective chokepoint is at runtime:
  • Call-budget + loop-detection on the agent's tool-call stream.
  • Flag tool outputs that emit self-referential "then call me again" checklists whose declared terminal condition never fires across repeated calls.
  • Monitor tool-return content, not just tool code and user prompts.
